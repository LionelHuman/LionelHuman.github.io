写在前面：为什么这篇博客值得你读完

如果你正在用 Kubernetes 跑微服务，迟早会撞上一堵墙：集群里几十个 Service，难道要给每个服务都开一个 NodePort 端口，再让客户去记一串 3xxxx 的数字？或者干脆买一堆 LoadBalancer，每个月给云厂商交一笔“端口税”？

这篇文章想带你把 Ingress 这件事从“知其然”讲到“知其所以然”，再用两个最常用的入口工具 Nginx Ingress Controller 和 Traefik 各做一组完整、可复现的实战案例。

关于环境：全文基于三台阿里云（中国香港）ECS 搭建的 K8s 集群
香港节点的好处是网络相对自由，拉取海外镜像、配置公网域名解析都更顺手，非常适合做对外暴露服务的实验。所有命令都在真实节点上跑通过

没有 Ingress 之前的世界：一个真实的痛点

假设集群里有两个服务：一个 Nginx（端口 80），一个 Tomcat（端口 8080），你想让它们都对外提供访问。在没有 Ingress 的年代，你手里只有两张牌：

  • NodePort：在每台节点上开一个高位端口（如 30080、30081），靠端口区分服务。缺点很直白——端口难记、端口不够用，而且无法让两个服务同时占用 80。
  • LoadBalancer：每个服务挂一个云厂商负载均衡器。功能没问题，但一个服务一个 LB，成本和运维负担都成倍上升。

更难受的场景是：你想让 www.myapp.com 这个域名的 80 端口同时承载“商品、用户、订单”三个微服务。端口是独占资源，无论 NodePort 还是 LoadBalancer 都做不到“一个 80 端口背后分流到多个服务”。唯一的笨办法是在集群外面再架一台传统负载均衡设备，手动配置代理规则——一旦有服务扩缩容、Pod 漂移，这套手动配置立刻失真。

Ingress 就是为了终结这种混乱而诞生的。

Ingress 到底是什么：先建立正确的心智模型

很多资料张口就说“Ingress 是用来暴露服务的”。这句话不准确——如果只是暴露服务，NodePort / LoadBalancer 早就能干，根本不需要 Ingress。

Ingress 真正的价值，在于把集群内部一套松散的微服务，对外包装成一个统一的整体：

  • 集群里每个微服务对应一个 Service；
  • 多个 Service 被一个 Ingress 组织起来，统一用一个域名（如 myapp.com）对外暴露；
  • 请求到达 Ingress 后，它根据域名（host） 和 路径（path） 这两类规则，把流量分发到不同的 Service。

所以你可以把 Ingress 理解成 Nginx 里的 location 配置块，只不过它是用 K8s 资源对象声明出来的“七层转发说明书”。

这里有一个极其关键、却被无数人忽略的事实：

Ingress 本身只是一套“转发规则说明书”，它不会真的帮你转发任何流量。

它就像一份产品说明书，写得再漂亮也不会自己跑起来。要让它真正干活，你必须安装 Ingress Controller（Ingress 控制器）——一个真正实现了转发逻辑的软件。

Ingress 与 Service 的区别：四层与七层的分野

维度 Service（ClusterIP/NodePort） Ingress
代理层级 四层（TCP/UDP，看 IP+端口） 七层（HTTP/HTTPS，看域名+URL 路径）
路由依据 IP + Port Host（域名）+ Path（路径）
典型用途 集群内部调用、单服务对外暴露 多服务统一域名入口、七层路由

一句话：Service 管“能不能连上端口”，Ingress 管“这个 URL 该交给谁处理”。

一次请求的完整链路

注意中间那句“内部集成了 Nginx”：目前主流 Ingress Controller（包括官方那个）底层都是用 Nginx 的七层反向代理 来实现转发的。这也回答了另一个常见疑问——“既然 Nginx 已经能七层代理了，为什么还要 Ingress？”因为你的应用以 Pod 形式跑在 K8s 里，Pod 随时可能被驱逐、销毁、重建、换 IP，外部一个静态的 Nginx 根本无法动态发现这些资源；而 Ingress Controller 会实时监听 K8s API，Pod 一变，转发规则自动跟着变。

Ingress Controller 家族全景图

Ingress Controller 不是 K8s 自带组件，而是一个统称，市面上有很多实现。当前由 K8s 官方维护的主要是 gce 和 ingress-nginx 两个，工业界用得最多的是 ingress-nginx。先建立“有哪些可选”的认知，后面重点实操前两个：

控制器 底层 语言 许可 一句话特点
Kubernetes Ingress Controller Nginx + Lua 插件 Go/Lua Apache 2.0 社区“官方”，最常见、最容易上手
NGINX Ingress Controller Nginx（无 Lua） Go Apache 2.0 NGINX 公司出品，稳定、向后兼容好，付费版功能多
Traefik 自研 Go MIT 为微服务动态环境而生，自动更新配置、自带 Web UI、内置 Let’s Encrypt

Voyager / Contour / Ambassador / Gloo / Skipper HAProxy / Envoy Go/Python Apache 2.0 各有侧重（L4 负载均衡、CRD 管理、API 微网关等），了解即可

Canary（金丝雀）发布：源自 20 世纪初英国矿工带金丝雀下矿——金丝雀对一氧化碳更敏感，一不安就预警避险。软件里同义：先发一小部分流量给新版本，发现 Bug 立即回滚，把爆炸半径降到最低。Traefik、Istio 等都原生支持。

换个玩家：认识 Traefik

Traefik 是一个为让微服务部署更便捷而生的现代 HTTP 反向代理 + 负载均衡工具。它最大特点是支持多种后台（Docker、Swarm、Kubernetes、Marathon、Consul、Etcd、Zookeeper、REST API、文件等）来自动化、动态地应用配置——后台服务一增一减，Traefik 的配置跟着自动更新，无需重启。

相比 Nginx Ingress Controller，Traefik 的吸引力在于：连续更新配置不重启、多种负载均衡算法、自带 Web UI（Dashboard）、指标导出、对金丝雀发布和 Let’s Encrypt 开箱即用。代价是为了高可用需要额外部署并连接一个 Key-value store。

部署 Traefik：记住“三权一配置，一入一规则”

Traefik 在 K8s 里要落地的资源，用一句口诀就能记全：

  • 三权：ServiceAccount + ClusterRole + ClusterRoleBinding，给 Traefik 访问 K8s 平台资源的权限。
  • 一配置：ConfigMap，配置 Traefik 的入口、启用哪些功能模块。
  • 一入：定义监控端口（如 80/443 接收流量、8080 看 Dashboard）。
  • 一规则：Ingress，定义请求来了转发到哪个 Service。

踩坑实录：404 背后的 API 版本兼容真相（高频踩坑）

如果你照上面配完，访问 traefik.itheima.com 仍然弹出 404 page not found，问题 99% 出在 Traefik 自身——它捕获不到请求过来的流量。排查思路：先看 Traefik 日志。

全文总结

  • Ingress 是一种转发规则，把用户请求按配置好的规则（域名 host + 路径 path）转发到后端 Pod 服务，类似 Nginx 的 location。它本身不转发，要配 Ingress Controller 才生效。
  • Service 是四层代理，Ingress 是七层代理；Ingress 的简写是 ing。
  • Ingress 的真正意义：把内部一套微服务对外包装成一个统一整体，外部只需访问一个入口。解决了 端口不好记、端口不够用 的问题。
  • 常见 Controller：社区官方 ingress-nginx（Nginx+Lua）、NGINX 公司版、Traefik（动态配置/自带 UI/内置证书）、HAProxy、Istio、Kong 等，按需选型。
  • Nginx Ingress 三案例：HTTP（多域名多 Service）、HTTPS（自签证书 + Secret + TLS）、NodePort（能用但不推荐）。
  • Traefik 口诀：三权（SA + Role + Binding）一配置（ConfigMap）一入（端口）一规则（Ingress）；用 DaemonSet 保证每台节点一个实例，8080 是 Dashboard，80 是入口。
  • 高频坑：K8s v1.22+ 移除了旧 Ingress API，老版 Traefik 会 404，必须升级到 v2.10.x 并把 RBAC 的 apiGroup 改成 networking.k8s.io。

把这一篇吃透，你对 K8s “南北向流量入口” 这件事，就从“会用一个 YAML”升级到“知道为什么这么配、出错往哪查”。三台阿里云香港节点这套环境，足够你把上面每个案例都亲手跑一遍——动手，才是学 K8s 唯一的捷径。
