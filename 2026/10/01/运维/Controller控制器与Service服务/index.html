从零开始精通 Kubernetes：控制器与 Service 深度解析

在 Kubernetes 的世界里，Pod 是最小的调度单元，但Pod 是一次性资源。如果它崩溃或被删除，不会自动重建。为了保证应用的高可用、弹性伸缩以及持续运行，我们需要更高级的抽象——控制器（Controller）。同时，由于 Pod 的 IP 地址不固定，我们需要一个稳定的访问入口——Service。

本文将由浅入深，带你全面掌握 Kubernetes 核心控制器与 Service 的实战用法。

为什么需要控制器

在 K8s 中，Controller 用于管理和维护 Pod。它的核心价值体现在：

  • 创建、删除和调度 Pod
  • 应用部署升级、版本回退、故障修复
  • 任务执行与调度

简而言之，控制器负责确保集群中 Pod 的实际状态与你期望的状态保持一致（例如：“始终运行 3 个 Nginx 副本”）

控制器分类与适用场景

K8s 提供了多种控制器，适用于不同的业务场景：

  • ReplicationController (RC)：早期机制，保证集群中始终运行 N 个副本。现已淘汰，建议使用 Deployment 替代。
  • ReplicaSet (RS)：RC 的增强版，支持基于集合的标签选择器。通常作为 Deployment 的底层实现，不直接使用。
  • Deployment：无状态应用的首选。控制 ReplicaSet，支持滚动升级、回滚等功能。例如：部署 Web 应用、微服务。
  • StatefulSet：有状态应用的救星。为每个 Pod 分配唯一标识符和稳定的网络域名，支持独立存储卷。例如：MySQL 集群、ZooKeeper 集群。
  • DaemonSet：节点级守护进程。保证所有（或特定）节点运行同一个 Pod。例如：日志收集 Filebeat、监控采集 node_exporter。
  • Job：一次性任务。执行一次即结束。例如：数据迁移、脚本执行。
  • CronJob：周期性任务。类似于 Linux 的 crontab。例如：定时数据同步、报表生成。

核心实战：Deployment 与 ReplicaSet

Deployment 是目前推荐使用的“控制器之王”。其架构关系为：Deployment 控制 ReplicaSet，ReplicaSet 控制 Pod。无状态应用具有所有 Pod 无差别、容器运行同一个 Image、无启动顺序先后之分、可随意扩容缩容的特点。

深入理解 Kubernetes Service

Service 为 Pod 客户端提供统一的访问入口，通过标签动态感知 Pod IP 地址变化，防止 Pod 失联。它通过 label-selector 关联 Pod，并实现 4 层（TCP/UDP）负载均衡。底层主要依靠 iptables 或 ipvs。

💡 专家提示：iptables 规则遍历匹配和更新呈线性时延；而 IPVS 工作在内核态，有更好的性能，且调度算法丰富（RR、WRR、LC、WLC、IP Hash）。在高并发场景下，建议将 kube-proxy 切换为 IPVS 模式。

Headless Service（无头服务）

普通的 ClusterIP 会分配虚拟 IP，而 Headless Service 不分配 ClusterIP，也不通过 kube-proxy 做反向代理和负载均衡。它通过 DNS 返回每个 Pod 的真实 IP 列表，非常适合 MySQL 主从、Kafka 节点间通信等有状态应用。

DNS 记录格式： <pod-name>.<service-name>.<namespace>.svc.cluster.local

NodePort：集群外部访问

在每个 Node 上分配一个端口作为外部访问入口。

验证：kubectl get svc 会看到 80:32334/TCP。此时可以通过 http://<任意节点IP>:32334 访问。

LoadBalancer 与 ExternalName

  • LoadBalancer：工作在特定的 Cloud Provider 上（如阿里云、AWS），会创建外部负载均衡器。适合生产环境。
  • ExternalName：将集群外部的服务引入到集群内部中来，实现集群内部 Pod 和集群外部服务的通信。缺点是不能指定端口。

💡 专家提示：集群内的 Pod 会继承 Node 上的 DNS 解析规则。所以只要 Node 可以访问的服务，Pod 中也可以访问到，这就实现了集群内服务访问集群外服务。

总结与进阶建议

  1. 控制器选择：无状态用 Deployment，有状态用 StatefulSet，节点守护用 DaemonSet，定时任务用 CronJob。
  2. Deployment 运维：熟练掌握 scale（扩缩容）、set image（升级）、rollout undo（回退）三大命令。
  3. Service 本质：Service 是 Pod 的固定门面。ClusterIP 用于内部，NodePort 用于本地/测试，LoadBalancer 用于生产，Headless 用于有状态服务发现。
  4. 底层模式：生产环境建议将 kube-proxy 从 iptables 切换为 IPVS 模式，以获得更好的负载均衡性能。

Kubernetes 的学习需要大量的实践。不要害怕 Pod 报错或 Pending，善用 kubectl describe 和 kubectl logs，在不断的排错中，你会逐渐掌握这个强大的云原生操作系统！
