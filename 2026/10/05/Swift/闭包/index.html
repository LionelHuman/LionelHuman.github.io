Swift 闭包：从一脸懵到真香，你只需要搞懂这三个阶段

很多新手写代码写到一定阶段，都会遇到一个绕不开的坎。你可能是想给数组排个序，或者是按条件筛选一下数据，结果写完发现代码里出现了一堆莫名其妙的符号：{ }、in、$0。

然后你去网上搜教程，他们管这个叫“闭包”。你看了一堆定义，什么“自包含的代码块”、“捕获上下文”、“引用类型”。每个字都认识，但连在一起就是不知道它在说啥。

我当年第一次看别人写的 SwiftUI 代码，里面全是 VStack { ... }、Button(action: { ... })，我当时甚至以为 { } 是某种 UI 容器的特殊语法，后来才知道，那玩意儿全是闭包。今天，我们就从最基础的地方起步，把闭包这颗硬骨头彻底啃下来。

闭包到底是个啥？先把它当函数看

在讲闭包之前，我们得先回顾一下之前学的函数。你可以把函数理解成一段“打包好的代码”，给它起个名字，需要用的时候直接喊名字就行。

但有的时候，你需要的只是一小段逻辑，不值得给它起个名字，甚至只会用一次。这时候，闭包就登场了。闭包本质上就是没有名字的函数，是一段“用完即走”的代码块。

避坑指南：别把 in 漏了
很多新手写闭包时，会习惯性地按照函数定义去写，写完了类型，顺手敲个回车就开始写代码，结果编译器无情报错。记住，闭包表达式里，参数和返回类型写完后，必须用 in 来隔开代码体，这是一个强制语法要求。

避坑指南：缩写参数不要用上瘾
虽然 $0、$1 看起来贼酷，但如果闭包体稍微长一点，或者参数多一点，千万别用缩写。试想一下，如果代码里全是 $0、$1、$2，过了两天你自己都不知道这些到底代表什么。超过两行的闭包，老老实实写参数名，in 前面多敲几个字母不会累死人。

新手最容易觉得闭包神奇，或者说“诡异”的地方，就是它能记住自己定义时周围环境里的变量，即使那个环境已经没了。

避坑指南：闭包和对象互相持有，会造成内存泄漏
上面这个例子虽然很神奇，但也隐藏着一个新手杀手——循环引用。如果闭包捕获的是一个类实例（比如 self），而这个类又持有这个闭包，它们俩就会互相“牵着手”永远不松手，导致内存泄漏。在 Swift 里，这就需要用 [weak self] 或者 [unowned self] 的捕获列表来解决。这是进阶话题，现在的你只需要知道有这个坑，等遇到了再查。

逃逸闭包：为什么异步任务需要它？

最后一个基础概念：逃逸闭包。

简单来说，如果一个闭包作为参数传入一个函数，但它在函数执行完之后才被调用，那么这个闭包就“逃逸”了。

什么时候会发生这种事？最常见的就是异步网络请求。你发起一个请求，函数立刻就返回了，但网络数据可能要几秒后才回来，那时候闭包才会被执行。

为了让编译器知道这个闭包可能会比函数活得久，你需要在参数类型前面加一个 @escaping 标记：

如果不加 @escaping，编译器会直接报错，因为闭包默认是不允许“逃逸”的。

避坑指南：在逃逸闭包里访问 self
如果一个逃逸闭包捕获了 self（比如在某个类的方法里发请求），必须显式写 self。这不是多此一举，而是编译器在提醒你：“注意了，这里可能会产生循环引用哦！” 比如在异步回调里更新 UI，你应该用 [weak self] in 或者 [unowned self] in 来明确捕获方式。
