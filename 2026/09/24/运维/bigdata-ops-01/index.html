大数据运维从入门到实战

很多新手一听到“大数据运维”，脑子里立刻浮现出成排的服务器和密密麻麻的代码，觉得特别高深

其实，再复杂的系统，也是由一个个基础概念拼装起来的今天，咱们就结合真实场景，从零开始，把大数据运维这条路给你铺平

什么是大数据与大数据运维

咱们先聊聊什么是大数据简单来说，就是那些太大、太复杂，传统数据库工具根本处理不了的数据

比如网上每一条评论、每一次点击、每一张图片，都是从社交媒体、购物平台、传感器里源源不断产生的它们数据量大、种类多、更新快

大数据存在的价值，核心就两点：解决海量数据的存储和海量数据的计算

大数据运维又是干嘛的？就是针对这些复杂的大数据系统，做运行和维护工作

你需要确保平台的稳定性、安全性和高效性具体包括监控系统健康度、优化存储和处理能力、搞数据备份和恢复、保障数据安全等

说白了，开发人员负责把系统建起来，运维人员负责让它一直稳稳当当跑下去

大数据的两个开发方向

大数据开发主要有两个方向——实时（在线开发）和非实时（离线开发），这也是你运维时需要对接的核心场景

离线开发：

非实时，定时批量处理。适合处理大量历史数据，如每日大规模用户行为分析

比如每天晚上跑一次大规模用户行为分析，或者每周做一次销售数据分析

常用Hadoop和Spark框架。优点是效率高，适合大批量数据；缺点是数据有延迟，结果不能马上看到

实时开发：

数据一产生立刻处理，几乎没有延迟。

适用于金融实时监控、社交媒体情绪实时分析等场景。常用Apache Kafka和Flink等流处理框架。

优点是能快速响应变化，适合实时决策；缺点是并发量大，对系统性能和稳定性要求极高，实现复杂，维护难度大

大数据技术栈全景图

做运维，心里必须有一张清晰的技术栈地图从数据源头到最终展示，整个链路长这样：

数据源层：离线主要靠业务数据库历史数据和Nginx等日志；实时则靠接口上报，比如家居设备、传感器、金融交易数据

数据采集层：离线用Sqoop、DataX、Kettle；实时用Flume、FlinkCDC、Canal、SeaTunnel

数据存储层：离线以HDFS为主；实时用Kafka负责传输，注意Kafka不负责长期保存

数据处理层：离线用Hive、Spark；实时用Flink、Doris、HUDI等

结果存储层：离线存到MySQL、PG或与实时组件保持一致；实时存到Doris、HUDI、ClickHouse等

数据应用层：最终用于数据可视化或者数据二次挖掘，也就是AI方向

统一定时调度平台：负责定时执行程序，主要用在离线平台，实时处理不需要定时常用组件是DolphinScheduler和Oozie

深入Hadoop核心架构

Hadoop是Apache旗下的一个用java语言实现开源软件框架，是一个开发和运行处理大规模数据的软件平台

允许使用简单的编程模型在大量计算机集群上对大型数据集进行分布式处理

Hadoop基于Java实现 => JDK

Hadoop属于Apache基金会（ASF）下的一个开源框架 => 开源 + 免费

Hadoop主要是对大数据集（数据量比较大 => 适合处理GB级别以上数据集）进行分布式（多台机器）处理

Hadoop是大数据运维的基石

狭义上，Hadoop指Apache这款开源框架，核心组件有三个：HDFS解决海量数据存储，YARN解决资源任务调度，MapReduce解决海量数据计算

Map：分，把大数据拆成多个部分单独算；Reduce：合，把每个Map的结果合并汇总得出最终结论

广义上，Hadoop是一个庞大的生态圈，随着发展，很多非Apache主管的项目也加入进来，对Hadoop做了很好的补充

这里必须搞懂一个概念：元数据描述数据的数据被称为元数据比如你在图书馆找书，记录书在几层、哪个书架的信息就是元数据；在Windows里，文件的盘符、目录、名字、大小、创建修改时间，也是元数据你拷贝一个大文件很慢，但删除却极快，因为底层删除的就是元数据

Hadoop架构演进与高可用

早期的Hadoop 1.x架构，存在单点故障问题集群里只有一个NameNode，一旦宕机整个集群就废了而且JobTracker工作量大，单节点压力大，容易出问题

到了Hadoop 2.x，引入了YARN和HA高可用架构生产环境的高可用集群里，节点角色分工非常明确：

HDFS集群：有两个NameNode，负责管理从节点和元数据信息还有N个DataNode，负责实际数据存储Zookeeper集群负责实现两个NameNode的主备切换当主节点宕机，备份节点通过Zookeeper的Watch监听机制感知到，从而把自己切换为主节点ZKFC进程负责让NameNode连接到Zookeeper集群，保持会话连接JournalNode集群只在HA架构中存在，用于保证多个NameNode的元数据一致，避免数据脑裂问题

Yarn集群：主节点ResourceManager可以有多个，但只能有一个主节点，其他都是备份它负责管理从节点、分配资源、接收计算任务并启动ApplicationMaster从节点NodeManager负责接收任务管理者的分配，占用资源运行任务主备切换同样依托Zookeeper集群

Zookeeper的核心机制

Zookeeper是Apache基金会旗下的开源免费软件，主要解决分布式集群中应用系统的一致性问题本质上是一个小文件存储系统

它的集群架构里有几个角色Leader是主节点，负责管理从节点、处理事务操作、将读取请求转发给从节点Follower是从节点，与主节点保持通信同步数据，负责非事务读取操作，将事务操作转发给主节点，并参与主节点投票Observer是观察者，一般不使用，目的是提升读取性能，参与非事务操作，但没有投票权

节点类型主要分四种，其实归为两类永久节点，会话开启关闭对它没影响，除非显式删除，否则一直存在，还能构建子节点临时节点，会话结束就自动删除，不允许构建子节点序列化节点创建时，如果目录下没有子节点，序号从0开始，每创建一个节点就自增+1，不管同名还是不同名目的就是保证记录同名称节点创建顺序，保证唯一性

Zookeeper的Watch机制非常关键你可以对某个节点进行监听，当节点发生状态变化时，Zookeeper会通知监听者可以监听节点的创建、修改、删除操作，也可以监听子节点的创建、修改、删除操作

安全组配置建议

⚠️ 生产环境安全提示

  1. 集群内部端口（2181、2888、3888、8020、8485、8019 等） 只需放行集群内网 IP 段（如 172.22.208.0/24），不要暴露到公网。这些端口一旦被公网扫描到，存在被恶意攻击的风险。
  2. Web UI 端口（9870、8088、9864、19888 等） 在做实验时为了方便，可以临时放行公网入方向。但在生产环境中，建议只通过公司内网 VPN 或跳板机访问。
  3. 如果图省事，在做实验时可以在安全组入方向临时设置“全部端口放行”，实验结束后再收紧规则。但绝不能在生产环境中这样做。

⚠️ 核心避坑指南（必看）

  1. 集群通信只用内网 IP：Hadoop、ZooKeeper 等组件之间的数据同步和心跳检测，必须使用内网 IP（即 172.22.208.x）。公网 IP 只用于你本地电脑 SSH 登录连接。如果配置文件中写成公网 IP，不仅会产生高额流量费，还会因为公网带宽有限导致集群通信超时、服务频繁掉线。
  2. 提前配置主机名映射：购买完成后，请立刻修改三台机器的主机名（hostnamectl set-hostname node1 等），并务必在三台机器的 /etc/hosts 中写入：
  3. 安全组放行：在阿里云控制台的安全组中，将三台机器的内网互通设为允许（默认通常互通），并放行公网入方向的 22 端口（用于 SSH），以及后续需要的 9870、8088、2181 等 Web UI 和通信端口。
准备步骤 为什么必须做
静态IP配置 集群内部通信极度依赖 IP，如果 IP 经常变动，节点互相找不到对方，集群直接瘫痪。
主机名和域名映射 配置文件里写主机名（如 node1）比写IP更好维护，也方便同事看懂配置。必须配hosts映射，否则主机名无法解析。
关闭防火墙和SELinux 大数据组件之间通信会开放大量内网端口，防火墙和 SELinux 会直接拦截这些通信，导致节点失联。
服务器免密配置 高可用架构中，NameNode主备切换、ZKFC隔离机制、批量分发脚本全靠免密登录，否则每次连接都要输密码，自动化无从谈起。
服务器时间同步 分布式系统需要根据时间戳判断心跳和事件顺序。时间不一致会导致ZooKeeper选举失败、NameNode脑裂、日志时间错乱等

⚠️ 新手避坑指南

  1. 自带的 OpenJDK 冲突：部分云服务器（如阿里云 CentOS 7.7）默认会自带 OpenJDK。如果 java -version 显示的不是你安装的版本，请先执行 rpm -qa | grep java 查看自带的包，并用 rpm -e --nodeps 包名 卸载它们。
  2. scp /etc/profile 的覆盖风险：上面的第 4 步直接覆盖了对方的 /etc/profile。这是建立在三台机器原本环境完全一致的前提下。如果 node2 或 node3 之前修改过该文件（比如添加了别的环境变量），直接覆盖会丢失原有配置。更安全但稍麻烦的做法是：每台机器分别手动执行第 2 步的 cat >> /etc/profile 追加命令。

  1. 主机名映射：必须配置 /etc/hosts，且阿里云必须用内网 IP。
  2. ZooKeeper 端口：必须放行 2181、2888、3888，否则 ZKFC 初始化会失败。

datanode的节点上下架

Hadoop集群的日常运维中，随着业务数据的增长，我们常常需要动态新增 DataNode来扩容存储，或者安全退役旧节点

为什么要动态上下架？

上架（扩容）：数据量增长，现有节点存储空间不足时，需要新增节点。

下架（退役）：硬件老化、故障或机房迁移，需要将节点上的数据安全迁移到其他节点后下线。

HDFS 原生支持这两个操作，无需停机，也不影响集群的正常读写

实战踩坑记录

坑一：加了白名单后，原有节点全掉线了

原因：一旦在 hdfs-site.xml 中配置了 dfs.hosts，NameNode 只接受白名单中的节点连接。如果你只添加了新节点，原有节点全部被拒绝。

解决：追加新节点前，先把所有旧节点写入 dfs_include.txt。

坑二：退役节点卡在 Decommission In Progress 不动了

原因：副本数不足（比如 dfs.replication=1），数据无处复制；或者网络不通，导致无法传输。

解决：先保证副本数 ≥ 2，再检查退役节点与存活节点之间的网络和防火墙。

坑三：HA 模式下，主备 NameNode 黑名单不一致

原因：只修改了 Active NameNode 的配置文件，忘记同步到 Standby。

解决：每次修改 dfs_include.txt 或 dfs_exclude.txt 后，都手动或通过脚本同步到所有 NameNode，并执行 hdfs dfsadmin -refreshNodes。

⚠️ 重要提醒：

如果你在 hdfs-site.xml 中配置了 dfs.hosts，那么所有 DataNode 都必须在这个文件中。否则未列入的节点会被 NameNode 拒绝连接。
