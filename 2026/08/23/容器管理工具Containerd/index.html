前言：为什么要学 Containerd？
如果你已经接触过 Docker，那你一定知道“容器”这个概念。但你可能没注意到，Docker 自身的底层容器管理能力，其实早已被 Containerd 取代——从 Kubernetes 1.20 版本开始，官方宣布不再推荐 Docker 作为容器运行时，转而默认支持 Containerd。
这意味着：
Containerd 是 Kubernetes 默认的容器运行时，是云原生技术栈的基石；
理解 Containerd，你才能真正搞懂 K8s 是如何创建、启动、销毁容器的；
无论你使用 Docker 还是 K8s，底层都离不开 Containerd 的身影。
所以，无论你是运维、开发还是 SRE，掌握 Containerd 都是必备技能。

Containerd 的前世今生（了解即可，但很重要）

云计算大背景（2006～2010）

2006 年，亚马逊推出 AWS，次年推出 S3 和 EC2，云计算开始萌芽。

2006 年，谷歌提出“云”的概念和理论。

2007 年，IBM 与谷歌联合多所大学明确提出“云计算”概念。

2008 年，微软发布 Windows Azure。

2010 年，OpenStack 开源计划成立。

云原生的概念是由cncf基金会在2015年前后首次提出来的

Docker 崛起与 Google 的“反击”

2013 年，Docker 公司推出 Docker 容器技术，迅速火爆全球。Google 感受到威胁，希望与 Docker 联合打造开源容器运行时，但被拒绝。

于是 Google 联合 RedHat、IBM 等，说服 Docker 将核心容器技术 libcontainer 捐给中立社区 OCI（Open Container Initiative），并更名为 runC。

2015 年，Google 牵头成立 CNCF（云原生计算基金会），并开源内部集群管理系统 Borg ——也就是今天大名鼎鼎的 Kubernetes（K8s）。

Kubernetes 迅速成为容器编排标准，Docker 虽然后期推出 Swarm，但败局已定。2017 年，Docker 公司宣布 原生支持 Kubernetes，并将自己的核心依赖 —— Containerd 捐献给 CNCF。

所以，Containerd 是 Docker 早期核心技术的延续，也是 CNCF 的正式成员。

Containerd 与 Docker、K8s 的关系图

Containerd 架构概览

Containerd 设计为嵌入型运行时，不直接面向终端用户（但我们可以用 ctr 调试）。

其两大子系统：

Bundle：容器的文件系统、配置、元数据打包。

Runtime：执行 Bundle，创建容器。

细化架构分为三大块：

Storage：镜像存储、快照管理。

Metadata：镜像和容器的元数据。

Runtime：任务管理、进程执行。

性能方面，Containerd 在启动、停止、删除容器上均优于 Docker 和 CRI-O（来自 benchmark 测试），更适合大规模集群场景。

容器管理（container + task + run）

Containerd 中容器的概念分为三层：

  • 镜像（Image）：只读模板，它包含了运行应用程序所需的所有文件、依赖项、环境变量和配置信息等。类似于软件安装包

  • 容器（Container）：静态配置对象（包含 rootfs、配置，但进程未启动）

  • 任务（Task）：真正运行的进程实例，它代表了容器内正在运行的进程

ctr container

总结与思考

关键知识点 说明
Container 定位 高级容器运行时，管理容器生命周期，向上对接 K8s/Docker，向下调用 runC
核心命令 ctrl（调试用）、crictl（K8s用）、docker（用户友好）
镜像操作 pull / ls / tag / push / export / import / rm
容器与任务 container（静态配置） + task（运行进程） = 真正的容器
命名空间 逻辑隔离，不同命名空间互不可见
私有仓库 需配置 hosts.toml 和 --plain-http
Docker 集成 修改 dockerd 启动参数即可共用 containerd
二进制安装 适合定制版本，注意 runC 单独下载

最后留一个思考题：为什么 Kubernetes 不再支持 Docker 作为运行时，却依然支持 Containerd？
答案就藏在 Containerd 的轻量、稳定和标准化的 OCI 兼容性中
