Kubernetes 集群安装部署

前言：为什么我们需要Kubernetes？

如果你已经使用过 Docker 或 Containerd，你可能已经体会到容器带来的轻量和便捷。但当你真正把容器应用到生产环境时，你会发现单机容器管理远远不够：

  • 容器宕机了，谁来自动重启？
  • 流量突增，如何一键扩容？
  • 新版本发布出现问题，如何快速回滚？
  • 多个容器之间如何互相发现和负载均衡？

这些问题的答案，就是 容器编排。而 Kubernetes（K8s）正是当今容器编排领域的绝对标准。

应用部署方式的演变

传统物理机部署

早期，应用程序直接跑在物理服务器上。问题很明显：

  • 资源争抢：多个应用共享一台物理机，一个应用可能耗尽 CPU 或内存，导致其他应用卡顿。
  • 成本高昂：每个应用单独占一台物理机，资源利用率极低，维护成本巨大。

优点：简单直接。
缺点：无资源隔离，扩展性差，成本高。

虚拟化部署

虚拟化技术（如 VMware、KVM）允许在一台物理机上运行多台虚拟机，每台 VM 拥有独立的操作系统和资源。

优点：
隔离性好：应用之间互不影响。
资源利用率提升：可以更灵活地分配硬件资源。
缺点：每台 VM 都需要完整的操作系统，占用大量磁盘、内存和 CPU，启动慢，浪费资源。

容器化部署

容器与 VM 类似，但 共享宿主机内核，更加轻量、启动快、资源效率高。每个容器拥有自己的文件系统、进程空间、网络栈，但无需额外操作系统。

容器化的优势：

  • 敏捷创建与部署
  • 持续集成与交付（CI/CD）友好
  • 开发、测试、生产环境一致性
  • 跨云、跨发行版可移植
  • 资源隔离与可预测性能

容器化也带来了新的挑战：如何管理成千上万个容器的生命周期、调度、伸缩、服务发现、故障恢复？ 这就催生了容器编排工具。

主流容器编排工具

  • Swarm：Docker 自带的编排工具，功能较简单，生态较弱。
  • Mesos + Marathon：Apache 项目，通用资源调度，但配置复杂。
  • Kubernetes（K8s）：Google 开源的基于 Borg 系统的容器编排平台，已成为事实标准

认识 Kubernetes

什么是 Kubernetes？

Kubernetes 源于希腊语，意为“舵手”或“飞行员”

Kubernetes是由 Google 开源的 容器集群管理系统，用于自动化部署、扩展和管理容器化应用

K8s这个缩写取自 k 和 s 之间 8 个字母

Kubernetes是基于容器技术（Docker）的分布式架构方案，用于自动化部署、扩展和管理容器化应用的开源系统

Kubernetes使用Go语言编写，源自谷歌内部保密多年的容器集群管理系统——Borg是其开源版本

Kubernetes2014年9月发布首个版本，2015年7月发布第一个正式版本

一切以服务（Service）为中心：Kubernetes不直接管理单个容器，而是将容器组合成逻辑单元（Pod）并通过 Service 对外暴露，围绕服务来构建系统架构

Kubernetes的本质是一组服务器集群，它可以在集群的每个节点上运行特定的程序，来对节点中的容器进行管理

Kubernetes官方网址：Kubernetes 官网

中文社区 Kubernetes 中文社区

核心定位：跨主机管理容器，提供以服务为中心的分布式架构支撑。

Kubernetes 的核心能力

  • 自我修复：容器崩溃后自动重启（约 1 秒内）。
  • 弹性伸缩：根据负载自动调整 Pod 副本数。
  • 服务发现与负载均衡：容器可通过 DNS 或环境变量发现彼此，并自动分发流量。
  • 版本回退：支持滚动更新，发布失败一键回滚。
  • 存储编排：自动挂载存储卷（如 NFS、云存储）。
  • 配置管理：通过 ConfigMap 和 Secret 管理配置和敏感信息。

Kubernetes 架构

K8s 集群采用 Master-Worker 架构

架构特征

  • 中心节点架构：Kubernetes 集群采用典型的 中心化控制 架构，由控制平面（Master）统一管控全局，工作节点（Node）负责执行。

集群组成（两大角色）

角色 别称 核心定位
控制节点 Master（主节点） 集群的“大脑”，负责全局管控，不直接运行业务容器（生产环境通常多主高可用）。
工作节点 Node（从属节点 / Minion） 集群的“手脚”，负责实际运行业务容器（Pod），执行具体计算任务。

各节点职责划分

  • Master（控制节点）职责：

    • 集群控制：作为运维人员管理整个 K8s 集群的统一入口。
    • 资源调度：决定将容器（Pod）分配到哪个 Node 上运行。
    • 副本控制：确保集群中运行的应用副本数量符合预期（例如始终维持 3 个实例）。
    • API 入口：提供统一的 REST API 接口，供用户、UI 或 CLI（kubectl）访问集群。

  • Node（工作节点）职责：

    • 执行工作负载：实际运行被调度的 Pod（容器组）。
    • 状态汇报：持续将本节点上容器的运行状态、资源使用情况上报给 Master。
    • 执行指令：接收并执行 Master 下发的命令，管理本地容器的完整生命周期（启动、停止、重启、销毁等）

Master 节点（控制平面组件）

Master 负责集群的决策、调度、状态维护，是集群的“大脑”。

组件 功能 关键特性
kubectl 官方CLI工具 与APIServer通信，将命令转为API请求，管理K8s资源
APIServer 集群唯一入口 接收REST请求（kubectl/UI等）；认证/授权；唯一直接读写etcd的组件
Scheduler Pod调度器 监听未调度Pod；预选+优选选出最优Node；结果写入etcd（经APIServer）
Etcd 分布式KV数据库 RAFT算法保一致性；半数以上存活即可用；存所有集群状态；组件通过List-Watch交互
Controller Manager 状态维护器 维护期望状态；故障检测/自动扩展/滚动更新；含RC、Node等

二、Node 节点（数据平面组件）

Node 负责实际运行业务容器，是集群的“手脚”。

组件 功能 特性
Kubelet 节点代理管理容器 上报状态,管理Pod,健康检查,cAdvisor监控
Kube Proxy 服务发现与负载均衡(4层) 内部发现,iptables/IPVS转发
Container Runtime 容器运行时引擎 Docker(旧),Containerd(新,效率高)

调用链演进（Docker → Containerd）

K8s 1.24 版本前后，容器运行时调用路径发生了显著变化：

旧路径（1.24 之前）

  • docker-shim 作为适配层，用于解耦 kubelet 与 docker 守护进程。

新路径（1.24 及以后）

  • 直接对接 Containerd，通过 CRI（容器运行时接口） 调用，无需 dockerd 和 docker-shim 中间层。
  • 优势：减少调用层级，启停容器更快、镜像拉取效率更高，且 Kubelet 迭代更敏捷。

核心工作机制总结

机制 说明
List-Watch 组件异步监听 ApiServer/etcd 资源变化，事件驱动协同
调度两阶段 预选（过滤节点）+ 优选（评分排序），完成 Pod 精准放置
声明式调谐 Controller Manager 比对期望与实际，通过 ApiServer 调谐

一句话记忆口诀

Master 决策调度存状态，Node 干活报告跑容器；
ApiServer 是唯一入口，etcd 存一切，kubelet 是监工，proxy 管网络，调度看 scheduler，稳定靠 controller。

Master节点组件（控制平面）

  • API Server：集群的统一入口，所有操作（kubectl、其他组件）都通过它进行认证、授权和访问控制。它是唯一能操作 etcd 的组件。
  • Scheduler：负责将新创建的 Pod 调度到合适的 Node 上，经过预选和优选两个阶段。
  • Controller Manager：维护集群状态，包括副本控制器、节点控制器、命名空间控制器等，确保实际状态与期望状态一致。
  • etcd：分布式键值存储，保存所有集群配置和状态数据（采用 Raft 协议，需奇数个节点）。

Worker节点组件（数据平面）

  • kubelet：每个 Node 上的核心代理，负责与 API Server 通信，管理 Pod 生命周期（创建、监控、销毁），并上报节点资源状态。
  • kube-proxy：实现 Service 的服务发现和四层负载均衡（基于 iptables/ipvs 规则）。
  • Container Runtime：实际运行容器的引擎，如 Docker、Containerd（K8s 1.24 后默认使用 Containerd）。

关键补充：Pod 是 Kubernetes 的最小调度单元，一个 Pod 内可包含多个紧密耦合的容器（共享网络和存储）。

组件交互流程（以部署 Nginx 为例）

  1. 用户通过 kubectl 向 API Server 提交部署请求。
  2. API Server 鉴权后将请求存入 etcd。
  3. Scheduler 监听未调度的 Pod，选择合适 Node 并绑定。
  4. 该 Node 上的 kubelet 收到通知，通过容器运行时创建并启动 Pod。
  5. kube-proxy 为 Service 配置网络规则，实现外部访问。
Kubernetes 部署 Nginx 服务 —— 完整组件调用流程
前置状态

Kubernetes集群启动之后，Master节点和Node节点都会将自身的信息（主机名、IP、资源容量等）自动注册并存储到 etcd数据库中，为后续调度和状态维护提供数据基础。

详细步骤

步骤 1：用户发起部署请求

运维人员通过kubectl命令行工具，向集群提交一个Nginx 服务的安装请求（通常是一个YAML或JSON格式的Deployment/Pod 定义）。

步骤 2：请求到达 ApiServer

该请求会首先被发送到 Master节点的ApiServer组件。

  • ApiServer 是整个集群的唯一入口，负责接收所有 REST API 请求。
  • 它会对请求进行认证、鉴权，并解析用户提交的期望状态（例如：要运行一个 Nginx 容器）。

步骤 3：调度决策（Scheduler 介入）

ApiServer 将调度请求（即“该把这个 Pod 放到哪个 Node 上？”）交给 Scheduler 组件。

  • Scheduler 会通过预选策略（过滤掉不满足资源、端口等条件的节点）和优选策略（对剩余节点进行打分排序）。
  • 最终选出一个最合适的 Node 节点，并将绑定结果（Pod 与 Node 的对应关系）写回 ApiServer。

步骤 4：控制器维护期望状态（Controller-Manager 介入）

ApiServer 调用 Controller-Manager 组件来维护集群的整体状态。

  • Controller-Manager 中的 Replication Controller 或 Deployment Controller 会确保Nginx的副本数量符合用户预期。
  • 它会持续监控当前 Pod 状态，如果发现 Pod 异常退出，会重新触发创建流程，确保服务始终可用。

步骤 5：Kubelet 执行并启动容器

目标 Node 节点上的 Kubelet 组件（相当于“监工”）接收到 ApiServer 下发的任务指令后，会通知本地的容器运行时（例如 Docker）来执行具体操作。

  • Docker（或 Containerd）会根据镜像仓库中的 Nginx 镜像，启动一个或多个容器。
  • 这些容器必须运行在 Pod 中。Pod 是 Kubernetes 的最小操作单元，是一组容器的集合，容器必须跑在Pod中，我们可以理解Pod就是容器的封装，一个Pod中可以有多个容器。

至此，一个 Nginx 服务就运行了。

步骤 6：对外暴露服务（Kube-Proxy 接入）

如果 Nginx 服务需要被集群外部的用户访问，就需要通过 Kube-Proxy 来提供访问代理。

  • Kube-Proxy 会在集群中创建对应的 Service（服务） 资源，并为该 Service 分配一个虚拟 IP（ClusterIP）。
  • 它通过维护节点上的 iptables 或 IPVS 规则，将外部或集群内部的访问流量，智能地转发到后端的 Nginx Pod 上。
  • 这样，外界用户就可以通过 Service 的 IP 或域名，无障碍地访问集群中运行的 Nginx 服务了。

🔍 补充说明（对照实际 K8s 机制）
  • 步骤 4 的补充：实际生产环境中，Controller-Manager 并不直接“调用 Node 安装”，而是通过声明式控制器模式持续调谐（Reconcile），确保实际状态始终趋近于用户定义的期望状态。
  • Pod 的地位：Pod 是容器的“外壳”，同一个 Pod 内的多个容器共享网络命名空间和存储卷，它们是“命运共同体”，通常用于部署紧密协作的辅助容器（如日志收集、流量代理等）。

Kubernetes Add-ons（附件/插件）详解

基本概念

Add-ons（附件） 是Kubernetes集群中的扩展组件，它们并非集群运行所必需的核心部分。即使不安装这些组件，Kubernetes集群依然可以正常工作，不影响基本的Pod调度和容器运行。但是，这些附件可以与主体程序很好地结合使用，为集群补齐网络、监控、日志、可视化、服务暴露等关键的生产级能力。

组件名称 核心功能

总结与延伸

知识点 要点
K8s 核心价值 自动化容器编排，解决生产环境运维痛点
架构关键组件 API Server、Scheduler、Controller Manager、etcd、kubelet、kube-proxy
部署工具选择 学习用 Minikube；单主生产用 kubeadm；多主高可用用 kubeasz
网络插件 Flannel 简单易用，适合入门；Calico 支持网络策略，适合生产
容器运行时 推荐 Containerd（K8s 1.24+ 默认），配置镜像加速可提升拉取速度
排错思路 先看节点状态，再看 Pod 日志，检查镜像拉取和网络互通

最后思考：为什么 Kubernetes 弃用 Docker 作为运行时，却拥抱 Containerd？
因为Docker包含大量非运行时必要功能（如构建镜像、日志驱动等），而Containerd更加轻量、稳定，且原生支持CRI（容器运行时接口），更符合 K8s的设计理念。
