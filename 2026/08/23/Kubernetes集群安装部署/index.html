Kubernetes 集群安装部署全攻略：从入门到生产级多主集群

前言：为什么我们需要 Kubernetes？

如果你已经使用过 Docker 或 Containerd，你可能已经体会到容器带来的轻量和便捷。但当你真正把容器应用到生产环境时，你会发现单机容器管理远远不够：

  • 容器宕机了，谁来自动重启？
  • 流量突增，如何一键扩容？
  • 新版本发布出现问题，如何快速回滚？
  • 多个容器之间如何互相发现和负载均衡？

这些问题的答案，就是 容器编排。而 Kubernetes（K8s）正是当今容器编排领域的绝对标准。

应用部署方式的演变（理解 K8s 出现的必然性）

传统物理机部署

早期，应用程序直接跑在物理服务器上。问题很明显：

  • 资源争抢：多个应用共享一台物理机，一个应用可能耗尽 CPU 或内存，导致其他应用卡顿。
  • 成本高昂：每个应用单独占一台物理机，资源利用率极低，维护成本巨大。

优点：简单直接。
缺点：无资源隔离，扩展性差，成本高。

虚拟化部署（VM）

虚拟化技术（如 VMware、KVM）允许在一台物理机上运行多台虚拟机，每台 VM 拥有独立的操作系统和资源。

优点：
隔离性好：应用之间互不影响。
资源利用率提升：可以更灵活地分配硬件资源。
缺点：每台 VM 都需要完整的操作系统，占用大量磁盘、内存和 CPU，启动慢，浪费资源。

容器化部署

容器与 VM 类似，但 共享宿主机内核，更加轻量、启动快、资源效率高。每个容器拥有自己的文件系统、进程空间、网络栈，但无需额外操作系统。

容器化的优势：

  • 敏捷创建与部署
  • 持续集成与交付（CI/CD）友好
  • 开发、测试、生产环境一致性
  • 跨云、跨发行版可移植
  • 资源隔离与可预测性能

容器化也带来了新的挑战：如何管理成千上万个容器的生命周期、调度、伸缩、服务发现、故障恢复？ 这就催生了容器编排工具。

主流容器编排工具

  • Swarm：Docker 自带的编排工具，功能较简单，生态较弱。
  • Mesos + Marathon：Apache 项目，通用资源调度，但配置复杂。
  • Kubernetes（K8s）：Google 开源的基于 Borg 系统的容器编排平台，已成为事实标准。

认识 Kubernetes（核心概念与架构）

什么是 Kubernetes？

Kubernetes 源于希腊语，意为“舵手”或“飞行员”

Kubernetes是由 Google 开源的 容器集群管理系统，用于自动化部署、扩展和管理容器化应用

K8s这个缩写取自 k 和 s 之间 8 个字母

Kubernetes是基于容器技术（Docker）的分布式架构方案，用于自动化部署、扩展和管理容器化应用的开源系统

Kubernetes使用Go语言编写，源自谷歌内部保密多年的容器集群管理系统——Borg是其开源版本

Kubernetes2014年9月发布首个版本，2015年7月发布第一个正式版本

一切以服务（Service）为中心：Kubernetes不直接管理单个容器，而是将容器组合成逻辑单元（Pod）并通过 Service 对外暴露，围绕服务来构建系统架构

Kubernetes的本质是一组服务器集群，它可以在集群的每个节点上运行特定的程序，来对节点中的容器进行管理

核心定位：跨主机管理容器，提供以服务为中心的分布式架构支撑。

Kubernetes 的核心能力

  • 自我修复：容器崩溃后自动重启（约 1 秒内）。
  • 弹性伸缩：根据负载自动调整 Pod 副本数。
  • 服务发现与负载均衡：容器可通过 DNS 或环境变量发现彼此，并自动分发流量。
  • 版本回退：支持滚动更新，发布失败一键回滚。
  • 存储编排：自动挂载存储卷（如 NFS、云存储）。
  • 配置管理：通过 ConfigMap 和 Secret 管理配置和敏感信息。

Kubernetes 架构（重点）

K8s 集群采用 Master-Worker 架构

架构特征

  • 中心节点架构：Kubernetes 集群采用典型的 中心化控制 架构，由控制平面（Master）统一管控全局，工作节点（Node）负责执行。

集群组成（两大角色）

角色 别称 核心定位
控制节点 Master（主节点） 集群的“大脑”，负责全局管控，不直接运行业务容器（生产环境通常多主高可用）。
工作节点 Node（从属节点 / Minion） 集群的“手脚”，负责实际运行业务容器（Pod），执行具体计算任务。

各节点职责划分

  • Master（控制节点）职责：

    • 集群控制：作为运维人员管理整个 K8s 集群的统一入口。
    • 资源调度：决定将容器（Pod）分配到哪个 Node 上运行。
    • 副本控制：确保集群中运行的应用副本数量符合预期（例如始终维持 3 个实例）。
    • API 入口：提供统一的 REST API 接口，供用户、UI 或 CLI（kubectl）访问集群。

  • Node（工作节点）职责：

    • 执行工作负载：实际运行被调度的 Pod（容器组）。
    • 状态汇报：持续将本节点上容器的运行状态、资源使用情况上报给 Master。
    • 执行指令：接收并执行 Master 下发的命令，管理本地容器的完整生命周期（启动、停止、重启、销毁等）

Master 节点（控制平面组件）

Master 负责集群的决策、调度、状态维护，是集群的“大脑”。

组件名称 核心功能 关键特性与细节
kubectl 官方 CLI 命令行工具 在 Master 上敲命令，与 ApiServer 通信
• 将用户输入转化为 ApiServer 能识别的 API 请求，实现对 K8s 资源的管理
ApiServer 所有操作的唯一入口 • 接收所有 REST API 请求（来自 kubectl、UI 或其他组件）
• 负责认证、授权、API 注册与发现
• 唯一能直接读写 etcd 的组件，其他组件操作 etcd 必须经过 ApiServer
Scheduler Pod 资源调度器 • 监听 ApiServer 获取未调度的 Pod 信息
• 通过 预选（基本条件过滤）和 优选（资源评分排序）两阶段选出最优 Node
• 调度结果写入 etcd（通过 ApiServer）
Etcd 分布式高性能 KV 数据库 • 用 Go 开发，基于 RAFT 算法 保证一致性
• 半数以上节点存活即可用（etcd 集群性能决定整个 K8s 集群规模）
• 存储所有集群状态数据（节点信息、Pod 部署信息、资源对象等）
• 各组件通过 List-Watch 机制 与 etcd 交互（异步消息监听）
Controller Manager 控制器管理器（状态维护） • 负责维护集群期望状态，实现故障检测、自动扩展、滚动更新等
• 包含多种子控制器：
- Replication Controller（副本数控制）
- Node Controller（节点状态监控）
- ResourceQuota Controller（资源配额）
- Namespace Controller
- ServiceAccount & Token Controller
- Service & Endpoints Controller（服务与端点维护）

二、Node 节点（数据平面组件）

Node 负责实际运行业务容器，是集群的“手脚”。

组件名称 核心功能 关键特性与细节
Kubelet（监工） 节点上的核心代理，管理容器生命周期 • 所有 Node 必备，与 ApiServer 通信汇报节点状态
• Pod 管理：监听 ApiServer 获取 Pod 期望状态，调用容器引擎达到该状态
• 容器健康检查：检测容器运行状态，根据重启策略处理异常
• 容器监控：通过 cAdvisor 采集节点资源使用数据，定期上报给 ApiServer（供调度决策）
Kube Proxy 服务发现与负载均衡（4 层） • 为 Service 资源提供集群内部的服务发现
• 实现 智能负载均衡，通过维护 iptables 或 IPVS 规则，将流量转发到后端 Pod
Container Runtime 容器运行时引擎 • Docker（1.24 版本前默认）
• Containerd（1.24 版本起默认），因效率更高、调用路径更短

调用链演进（Docker → Containerd）

K8s 1.24 版本前后，容器运行时调用路径发生了显著变化：

旧路径（1.24 之前）

  • docker-shim 作为适配层，用于解耦 kubelet 与 docker 守护进程。

新路径（1.24 及以后）

  • 直接对接 Containerd，通过 CRI（容器运行时接口） 调用，无需 dockerd 和 docker-shim 中间层。
  • 优势：减少调用层级，启停容器更快、镜像拉取效率更高，且 Kubelet 迭代更敏捷。

核心工作机制总结

机制 说明
List-Watch 机制 所有组件与 ApiServer/etcd 之间采用异步消息监听模式，组件“监听”自己关心的资源变化事件，实现事件驱动式协同。
调度两阶段 Scheduler 通过 预选（筛选合格节点） + 优选（计算最优节点）完成 Pod 的精准放置。
声明式状态维护 Controller Manager 不断比对“期望状态”（YAML 定义）与“实际状态”（etcd 存储），并通过 ApiServer 进行调谐（Reconcile）。

一句话记忆口诀

Master 决策调度存状态，Node 干活报告跑容器；
ApiServer 是唯一入口，etcd 存一切，kubelet 是监工，proxy 管网络，调度看 scheduler，稳定靠 controller。

Master节点组件（控制平面）

  • API Server：集群的统一入口，所有操作（kubectl、其他组件）都通过它进行认证、授权和访问控制。它是唯一能操作 etcd 的组件。
  • Scheduler：负责将新创建的 Pod 调度到合适的 Node 上，经过预选和优选两个阶段。
  • Controller Manager：维护集群状态，包括副本控制器、节点控制器、命名空间控制器等，确保实际状态与期望状态一致。
  • etcd：分布式键值存储，保存所有集群配置和状态数据（采用 Raft 协议，需奇数个节点）。

Worker节点组件（数据平面）

  • kubelet：每个 Node 上的核心代理，负责与 API Server 通信，管理 Pod 生命周期（创建、监控、销毁），并上报节点资源状态。
  • kube-proxy：实现 Service 的服务发现和四层负载均衡（基于 iptables/ipvs 规则）。
  • Container Runtime：实际运行容器的引擎，如 Docker、Containerd（K8s 1.24 后默认使用 Containerd）。

关键补充：Pod 是 Kubernetes 的最小调度单元，一个 Pod 内可包含多个紧密耦合的容器（共享网络和存储）。

组件交互流程（以部署 Nginx 为例）

  1. 用户通过 kubectl 向 API Server 提交部署请求。
  2. API Server 鉴权后将请求存入 etcd。
  3. Scheduler 监听未调度的 Pod，选择合适 Node 并绑定。
  4. 该 Node 上的 kubelet 收到通知，通过容器运行时创建并启动 Pod。
  5. kube-proxy 为 Service 配置网络规则，实现外部访问。
Kubernetes 部署 Nginx 服务 —— 完整组件调用流程
前置状态

Kubernetes 集群启动之后，Master 节点和 Node 节点都会将自身的信息（主机名、IP、资源容量等）自动注册并存储到 etcd 数据库中，为后续调度和状态维护提供数据基础。

详细步骤

步骤 1：用户发起部署请求

运维人员通过 kubectl 命令行工具，向集群提交一个Nginx 服务的安装请求（通常是一个 YAML 或 JSON 格式的 Deployment/Pod 定义）。

步骤 2：请求到达 ApiServer

该请求会首先被发送到 Master 节点的 ApiServer 组件。

  • ApiServer 是整个集群的唯一入口，负责接收所有 REST API 请求。
  • 它会对请求进行认证、鉴权，并解析用户提交的期望状态（例如：要运行一个 Nginx 容器）。

步骤 3：调度决策（Scheduler 介入）

ApiServer 将调度请求（即“该把这个 Pod 放到哪个 Node 上？”）交给 Scheduler 组件。

  • Scheduler 会通过预选策略（过滤掉不满足资源、端口等条件的节点）和优选策略（对剩余节点进行打分排序）。
  • 最终选出一个最合适的 Node 节点，并将绑定结果（Pod 与 Node 的对应关系）写回 ApiServer。

步骤 4：控制器维护期望状态（Controller-Manager 介入）

ApiServer 调用 Controller-Manager 组件来维护集群的整体状态。

  • Controller-Manager 中的 Replication Controller 或 Deployment Controller 会确保 Nginx 的副本数量符合用户预期。
  • 它会持续监控当前 Pod 状态，如果发现 Pod 异常退出，会重新触发创建流程，确保服务始终可用。

步骤 5：Kubelet 执行并启动容器

目标 Node 节点上的 Kubelet 组件（相当于“监工”）接收到 ApiServer 下发的任务指令后，会通知本地的容器运行时（例如 Docker）来执行具体操作。

  • Docker（或 Containerd）会根据镜像仓库中的 Nginx 镜像，启动一个或多个容器。
  • 这些容器必须运行在 Pod 中。Pod 是 Kubernetes 的最小操作单元，是一组容器的集合，容器必须跑在 Pod 中，我们可以理解 Pod 就是容器的封装，一个 Pod 中可以有多个容器。

至此，一个 Nginx 服务就运行了。

步骤 6：对外暴露服务（Kube-Proxy 接入）

如果 Nginx 服务需要被集群外部的用户访问，就需要通过 Kube-Proxy 来提供访问代理。

  • Kube-Proxy 会在集群中创建对应的 Service（服务） 资源，并为该 Service 分配一个虚拟 IP（ClusterIP）。
  • 它通过维护节点上的 iptables 或 IPVS 规则，将外部或集群内部的访问流量，智能地转发到后端的 Nginx Pod 上。
  • 这样，外界用户就可以通过 Service 的 IP 或域名，无障碍地访问集群中运行的 Nginx 服务了。

🔍 补充说明（对照实际 K8s 机制）
  • 步骤 4 的补充：实际生产环境中，Controller-Manager 并不直接“调用 Node 安装”，而是通过声明式控制器模式持续调谐（Reconcile），确保实际状态始终趋近于用户定义的期望状态。
  • Pod 的地位：Pod 是容器的“外壳”，同一个 Pod 内的多个容器共享网络命名空间和存储卷，它们是“命运共同体”，通常用于部署紧密协作的辅助容器（如日志收集、流量代理等）。

Kubernetes Add-ons（附件/插件）详解

基本概念

Add-ons（附件） 是 Kubernetes 集群中的扩展组件，它们并非集群运行所必需的核心部分。即使不安装这些组件，Kubernetes 集群依然可以正常工作，不影响基本的 Pod 调度和容器运行。但是，这些附件可以与主体程序很好地结合使用，为集群补齐网络、监控、日志、可视化、服务暴露等关键的生产级能力。

常见 Add-ons 分类与介绍

1️⃣ 网络与 DNS 服务
组件名称 核心功能
CoreDNS / kube-dns 负责为整个集群提供内部 DNS 服务。通过域名解析，让 Pod 和 Service 之间可以通过名称（而非 IP）进行互相访问。
2️⃣ 服务暴露与流量入口
组件名称 核心功能
Ingress Controller 为集群中的 Service 提供外部访问入口（七层负载均衡）。它可以将外部域名（如 www.itheima.com）的请求，根据路由规则转发到集群内部的对应 Service，再最终路由到后端的 Pod 和容器中，是实现对外发布服务的关键组件。
3️⃣ 监控与性能管理
组件名称 核心功能
Heapster / Metrics-Server 提供集群资源监控数据（如 Pod 和 Node 的 CPU、内存使用情况）。Metrics-Server 是 Heapster 的替代者，主要负责采集核心指标，为 HPA（水平自动伸缩）等能力提供数据支撑。
Prometheus + Grafana Prometheus 是一个开源的系统监控和警报工具包，具有强大的数据模型和查询语言（PromQL），能够抓取和存储时序指标数据；Grafana 是一个开源的可视化工具，它可以与 Prometheus 集成，将监控数据以丰富的图表形式进行展示，实现高度定制化的监控看板。
4️⃣ 可视化管理
组件名称 核心功能
Dashboard 提供 Kubernetes 集群的 Web 可视化界面。用户可以通过该界面在浏览器中直观地查看、管理集群中的各种资源（Pod、Service、Deployment 等），并进行简单的运维操作。
5️⃣ 集群扩展与容灾
组件名称 核心功能
Federation 提供跨可用区（Zone）或跨地域（Region）的集群管理能力。通过 Federation，可以将多个 Kubernetes 集群联合成一个逻辑上的大集群，实现多云/混合云架构下的应用高可用和容灾。
6️⃣ 日志采集、存储与查询（EFK / ELK Stack）

该领域涉及一组协同工作的组件，用于处理集群内海量的容器日志：

组件名称 核心功能
Elasticsearch 一个分布式搜索和分析引擎，用于存储大量的日志和监控数据，支持快速的全文检索和数据分析。
Logstash / Fluentd 数据采集与处理管道。Logstash（或 Fluentd）可以收集各个 Pod 和 Node 上产生的日志数据，对日志进行过滤、解析和格式化，然后将其发送到 Elasticsearch 中存储。
Kibana 一个可视化工具，专门用于在 Elasticsearch 中查询、分析和展示日志数据，提供友好的 Web 交互界面。

补充说明：当使用 Fluentd 替代 Logstash 时，这套组合通常被称为 EFK Stack；使用 Logstash 时则称为 ELK Stack。二者功能类似，均广泛用于 Kubernetes 日志监控体系。

三、总结

类别 代表组件 目的
服务发现与网络 CoreDNS 集群内部域名解析
流量入口 Ingress Controller 外部 HTTP/HTTPS 流量路由
资源监控 Metrics-Server, Prometheus 采集和存储性能指标
可视化展示 Dashboard, Grafana, Kibana 提供 Web UI 图表展示
日志处理 Fluentd/Logstash + Elasticsearch 日志收集、存储与查询
集群联邦 Federation 跨可用区的高可用管理

Kubernetes 集群部署方式对比

部署方式 适用场景 优点 缺点
Minikube 本地开发测试 简单一键启动 仅单节点，不适合生产
Kubeadm 中小型生产、学习 官方工具，标准化，易操作 细节屏蔽，排错较难
Kubeasz 生产级多主高可用 基于 Ansible，自动化部署多主多从，支持国内网络优化 需了解 Ansible

本文重点介绍 kubeadm（单主入门）和 kubeasz（多主生产级）两种方式。

实战 —— 使用 Kubeadm 部署单主 Kubernetes 集群

总结与延伸

知识点 要点
K8s 核心价值 自动化容器编排，解决生产环境运维痛点
架构关键组件 API Server、Scheduler、Controller Manager、etcd、kubelet、kube-proxy
部署工具选择 学习用 Minikube；单主生产用 kubeadm；多主高可用用 kubeasz
网络插件 Flannel 简单易用，适合入门；Calico 支持网络策略，适合生产
容器运行时 推荐 Containerd（K8s 1.24+ 默认），配置镜像加速可提升拉取速度
排错思路 先看节点状态，再看 Pod 日志，检查镜像拉取和网络互通

最后思考：为什么 Kubernetes 弃用 Docker 作为运行时，却拥抱 Containerd？
因为 Docker 包含大量非运行时必要功能（如构建镜像、日志驱动等），而 Containerd 更加轻量、稳定，且原生支持 CRI（容器运行时接口），更符合 K8s 的设计理念。
