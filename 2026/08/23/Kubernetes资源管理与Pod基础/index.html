【掌握】资源管理介绍

YAML 语言介绍

YAML 是一个类似 XML、JSON 的标记性语言，强调以数据为中心，号称“一种人性化的数据格式语言”。

YAML 核心规则：

  • 大小写敏感
  • # 表示注释
  • 使用空格缩进（不要用 Tab），缩进空格数不重要，但相同层级的元素必须左对齐
  • 书写时 key: value 冒号后必须加一个空格
  • 多段 YAML 配置放在一个文件中时，中间使用 --- 分隔

数据类型

标量类型（Scalar Types）：单个的、不可再分的值

序列类型（Sequence Types）：一组按次序排列的值，即数组/列表

映射类型（Mapping Types）：键值对的集合，即字典/Hash

三种数据类型可以随意组合嵌套，生成丰富的 YAML 数据形式。可用在线工具 https://www.json2yaml.com/convert-yaml-to-json 验证 YAML 格式。

资源管理方式

在Kubernetes中，所有内容都抽象为资源，用户通过操作资源来管理K8s

容器、Pod、存储的关系

  • 容器：K8s 本质上是一个集群系统，部署服务就是在集群中运行一个个容器
  • Pod：K8s 的最小管理单元是 Pod 而不是容器，容器必须放在 Pod 中；K8s一般不直接管理Pod，而是通过Pod控制器（如 Deployment）来管理
  • Service：Pod 提供服务后，通过 Service 实现访问
  • 存储：ConfigMap、Secret 等提供配置和数据持久化

三种资源管理方式

类型 操作对象 适用环境 优点 缺点
命令式对象管理 对象 测试 简单 只能操作活动对象，无法审计、跟踪
命令式对象配置 文件 开发 可以审计、跟踪 项目大时配置文件多，操作麻烦
声明式对象配置 文件或目录 开发 支持目录操作 意外情况下难以调试

小结：

  1. 命令式和声明式是 Kubernetes 常见的两种资源管理方式
  2. 命令式适合测试和调试，由于没有审计和跟踪记录，生产上很少用
  3. 声明式 apply 支持版本管理和操作记录

Namespace（命名空间）

Namespace 的主要作用是实现多套环境的资源隔离或多租户的资源隔离

kubernetes通过将集群内部的资源分配到不同的Namespace中，可以形成逻辑上的”组”，以方便不同的组的资源进行隔离使用和管理

默认命名空间：

  • default：未指定 Namespace 的对象默认在此
  • kube-node-lease：集群节点心跳维护（v1.13+）
  • kube-public：可以被所有人访问（包括未认证用户）
  • kube-system：Kubernetes 系统创建的资源

Service（服务发现/负载均衡）

Pod IP会随着Pod重建而变化，且仅集群内可见外部无法访问。Service提供固定的访问入口并实现负载均衡

Service可以看作是一组同类Pod对外的访问入口。借助Service，应用可以方便地实现服务发现和负载均衡

servuce可以通过集群内部或外部的网络访问这些pod。主要的作用就是让容器能够向外暴露端口，对外进行访问

Service资源可以聚合提供相同服务的多个Pod，并为它们提供一个统一的入口地址。

这样通过访问Service的入口地址，就可以访问到后台的Pod服务，而无需关心每个Pod的IP地址的变化

Service 类型：

  • ClusterIP（默认）：仅在集群内部可访问

  • LoadBalancer：云环境使用，外部负载均衡路由到 NodePort 和 ClusterIP
  • ExternalName：代理集群外部服务

【掌握】Pod 基础

Pod基本概念

Pod 与 Docker、Container 的关系：

  • Docker 是容器引擎，Container 是容器
  • Pod 是 K8s 最小的管理单位，封装一个或多个容器

核心特性：

  • 一个 Pod 里的多个容器共享存储和网络，可看作一个逻辑主机
  • 多个容器共享同一个 network namespace，共享 Pod IP 和端口，可通过 localhost 通信（注意端口不冲突）
  • 不同 Pod 有不同 IP，不同 Pod 间通信使用 Pod IP
  • 一个 Pod 里的多个容器可以共享存储卷

Pod 的组成部分：

  • 用户程序容器：一个或多个，运行具体应用进程
  • Pause 容器（根容器）：每个 Pod 都有一个，维护 Pod 网络协议栈，负责 Pod 生命周期管理。Pause 容器的生命周期与 Pod 相同，创建 Pod 时同时创建，删除 Pod 时同时删除。

Pod 的分类：

  • 自主式 Pod：无控制器管理，删除后不会重新创建
  • 控制器管理的 Pod：控制器按策略控制 Pod 数量，少了自动创建，多了自动删除
    • Deployment：部署无状态应用，管理 Pod 创建和更新
    • ReplicaSet：确保 Pod 副本数量（一般随 Deployment 创建）
    • DaemonSet：保证每个节点都运行一个 Pod 副本
    • StatefulSet：管理有状态应用，提供稳定网络标识和存储

重启策略 restartPolicy：

  • Always：容器挂了总是重启（默认）
  • OnFailure：容器状态为错误时才重启（非 0 退出码）
  • Never：容器挂了不予重启

Always 策略采用线性回退算法：第一次立即重启，再挂等 10s，第三次等 20s，依次类推。

最后思考：为什么 Pod 是 K8s 的最小调度单元而不是容器？

因为 Pod 封装了多个共享资源的容器，使得容器间可以高效通信（localhost）和共享存储，这比单独调度每个容器更符合实际微服务架构的需求。Pause 容器作为根容器，维护了 Pod 的网络命名空间，让所有用户容器共享同一个 IP 和网络栈。

Kubernetes 集群安装部署全攻略：从入门到生产级多主集群前言：为什么我们需要 Kubernetes？如果你已经使用过 Docker 或 Containerd，你可能已经体会到容器带来的轻量和便捷。但当你真正把容器应用到生产环境时，你会发现单机容器管理远远不够： 容器宕机了，谁来自动重启？ 流量突增，如何一键扩容？ 新版本发布出现问题，如何快速回滚？ 多个容器之间如何互相发现和负载均衡？ 这些问题的答案，就是 容器编排。而 Kubernetes（K8s）正是当今容器编排领域的绝对标准。 应用部署方式的演变（理解 K8s 出现的必然性）传统物理机部署早期，应用程序直接跑在物理服务器上。问题很明显： 资源争抢：多个应用共享一台物理机，一个应用可能耗尽 CPU 或内存，导致其他应用卡顿。 成本高昂：每个应用单独占一台物理机，资源利用率极低，维护成本巨大。 优点：简单直接。缺点：无资源隔离，扩展性差，成本高。 虚拟化部署（VM）虚拟化技术（如 VMware、KVM）允许在一台物理机上运行多台虚拟机，每台 VM 拥有独立的操作系统和资源。 优点：隔离性好：应用之间互不...
