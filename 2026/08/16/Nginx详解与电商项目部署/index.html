Nginx升级完全指南：从”停机重装”到”丝滑不停服”

在日常工作中，我们经常会遇到这样的情况：Nginx出了新版本，修复了重大漏洞，或者我们需要用到旧版本没有的新模块。升级是刚需，但线上服务器每停一秒，可能就损失真金白银。

前置认知：kill 命令的”第二人格”

很多新手认为 kill 就是”杀死进程”。这是一个致命的误解！

kill 命令的底层本质其实是 “给进程传递一个信号”。就好比你给同事发微信：

发”立刻下班”（kill -9）→ 强制杀死

发”干完手头活就下班”（kill -15）→ 优雅退出

发”重启电脑”（kill -HUP）→ 重载配置

正是因为 kill -9 和 kill -15 用得太多，给了我们”kill只能杀进程”的错觉。事实上，Nginx的平滑升级就是巧妙地利用特定信号来实现的

Nginx 七大核心信号详解

操作Nginx之前，你必须先看懂下面这张信号表。这是运维老手和新手的分水岭

信号参数 官方含义 大白话翻译 实战场景
-TERM / -INT 快速退出 “立刻停！” —— 不管手头有没有活，马上终止进程。 紧急情况强制关闭（不太优雅，不推荐）。
-QUIT 优雅退出 “干完活再下班” —— 处理完当前正在进行的请求后，再退出进程。 关闭Nginx时首选此方式，对用户影响最小。
-HUP 重载配置文件 “重新读一遍配置” —— 用新配置启动新Worker，并优雅关闭旧Worker。 修改了 nginx.conf 后，用此信号重载（等价于 nginx -s reload）。
-USR1 重新打开日志文件 “换个新本子记日志” —— 重新打开日志文件句柄。 日志切割（轮转）时的核心命令，配合 mv 移动旧日志后使用。
-USR2 平滑升级二进制 “升级程序本体” —— 启动一个新的主进程（Master），新老版本共存。 不停服升级的第一步。
-WINCH 优雅关闭子进程 “辞退所有基层员工” —— 关闭主进程（Master）下的所有工作进程（Worker）。 升级过程中，让旧版本的Worker不再接收新请求。
-QUIT （再提一次） 优雅退出主进程 “老板退休” —— 彻底关闭主进程（Master）。 升级完成后，送走旧版本的”老老板”。

记忆口诀：老板（Master）管员工（Worker）
-WINCH 是辞退所有老员工（Worker），但老板（Master）还在
-QUIT 是老板（Master）正式退休，彻底退出

方案一：重装升级（停机升级）

这是最原始、最简单的方式，但需要停服

操作步骤：

停止Nginx服务

删除旧的安装目录（rm -rf /usr/local/nginx）

下载新版本源码包，重新编译安装

适用场景：

开发环境或测试环境

线上业务允许短暂停机的维护窗口

风险提示：

操作前务必备份配置文件（conf/ 目录）和网站资源文件（html/ 目录），否则删库跑路的就是你

方案二：平滑升级（不停服升级）

核心原理（三阶段法则）

平滑升级不停止旧服务，核心逻辑就三步：

旧的不停：保持老版本Nginx继续处理当前请求

新的起来：编译新版本，启动新的主进程（Master）

平稳交接：新老Master同时运行，新的接手新请求，旧的处理完老请求后优雅退场

前言:Nginx是什么？为什么每个后端开发都要会它？

Nginx是一个高性能的HTTP和反向代理服务器，用于负载均衡，静态内容缓存，以及动态内容生成

先问大家一个问题：你写了一个PHP/Java/Python项目，怎么让外网用户访问到？

答案很简单——需要一个 Web服务器 来接收HTTP请求，再把处理结果返回给浏览器。Nginx就是目前最流行的Web服务器之一，它轻量、高并发、配置灵活，全球超过4亿个网站跑在Nginx上

打个比方：Nginx就像商场的前台小姐姐——用户来了（HTTP请求），她先判断你要去哪个楼层（路由分发），再把你的需求转给对应的柜台（后端应用），最后把结果告诉你

今天这篇教程，我会带你从零基础开始，一步步掌握Nginx的核心用法，最后用宝塔面板部署一套完整的NiuShop电商系统，让你真正体会“学以致用”

Nginx的两种管理方式（千万别混用！）

新手最常踩的坑：systemctl 和 sbin/nginx 混用导致各种诡异报错

管理方式 启动 重载配置 停止 适用场景

⚠️ 铁律：选一种就别换！我见过同学用 ./sbin/nginx 启动，然后敲 systemctl reload nginx，结果报错 nginx: [emerg] bind() to 0.0.0.0:80 failed —— 因为 systemd 和原生进程互相抢端口

配置文件层级结构

http：整个服务器只有1个，管全局

server：可以有多个，每个管一个网站（虚拟主机）

location：每个server里可以有多个，每个管一类URL路径

第一块：全局配置（影响Nginx进程本身）

新手理解：worker_processes 相当于Nginx雇了几个“工人”来处理请求。工人越多，同时能干的活越多，但也要看CPU有多少个“手”

第二块：events（网络连接相关）

新手理解：worker_connections 乘以 worker_processes 就是你服务器的最大并发连接数。上面这个配置 = 1 × 1024 = 1024个并发

第三块：http（核心大本营）

location匹配规则（新手最容易搞混的）

location 的匹配规则有优先级，我用一张表帮你理清：

写法 含义 优先级
location = /xxx 精确匹配，完全一致才命中 最高
location ^~ /xxx 前缀匹配，一旦命中就不再看正则 第二
location ~ \.php$ 正则匹配，区分大小写 第三
location ~* \.jpg$ 正则匹配，不区分大小写 第三
location /xxx 普通前缀匹配 第四
location / 默认匹配，所有没命中的都走这里 最低

访问 example.com/index.php → 命中③
访问 example.com/about.html → 命中④

虚拟主机

为什么要用虚拟主机？

先问一个问题：你只有一台服务器，但手上同时有三个项目要上线，怎么办？
方案A：买三台服务器 → 钱包不同意 ❌
方案B：一台服务器跑三个Nginx实例 → 端口打架，管理混乱 ❌
方案C：一台服务器、一个Nginx、配置三个虚拟主机 → 这才是正道 ✅

这就是虚拟主机的价值所在——让一台物理服务器同时承载多个网站，每个网站拥有独立的域名、独立的目录、独立的配置，彼此互不干扰

用户访问不同的域名，Nginx会根据请求头里的域名自动路由到对应的网站目录，用户完全感觉不到这些网站跑在同一台机器上

如果输出中包含 master process /usr/local/nginx/sbin/nginx，说明是用 sbin/nginx 方式启动的。

原因： server 块被错误地放在了 http 块外面。
