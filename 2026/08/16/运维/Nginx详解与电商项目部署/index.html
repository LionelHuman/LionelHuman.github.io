Nginx升级完全指南：从”停机重装”到”丝滑不停服”

在日常工作中，我们经常会遇到这样的情况：Nginx出了新版本，修复了重大漏洞，或者我们需要用到旧版本没有的新模块。升级是刚需，但线上服务器每停一秒，可能就损失真金白银。

前置认知：kill 命令的”第二人格”

很多新手认为 kill 就是”杀死进程”。这是一个致命的误解！

kill 命令的底层本质其实是 “给进程传递一个信号”。就好比你给同事发微信：

发”立刻下班”（kill -9）→ 强制杀死

发”干完手头活就下班”（kill -15）→ 优雅退出

发”重启电脑”（kill -HUP）→ 重载配置

正是因为 kill -9 和 kill -15 用得太多，给了我们”kill只能杀进程”的错觉。事实上，Nginx的平滑升级就是巧妙地利用特定信号来实现的

Nginx 七大核心信号详解

操作Nginx之前，你必须先看懂下面这张信号表。这是运维老手和新手的分水岭

信号参数 官方含义 大白话翻译 实战场景
-TERM / -INT 快速退出 “立刻停！” —— 不管手头有没有活，马上终止进程。 紧急情况强制关闭（不太优雅，不推荐）。
-QUIT 优雅退出 “干完活再下班” —— 处理完当前正在进行的请求后，再退出进程。 关闭Nginx时首选此方式，对用户影响最小。
-HUP 重载配置文件 “重新读一遍配置” —— 用新配置启动新Worker，并优雅关闭旧Worker。 修改了 nginx.conf 后，用此信号重载（等价于 nginx -s reload）。
-USR1 重新打开日志文件 “换个新本子记日志” —— 重新打开日志文件句柄。 日志切割（轮转）时的核心命令，配合 mv 移动旧日志后使用。
-USR2 平滑升级二进制 “升级程序本体” —— 启动一个新的主进程（Master），新老版本共存。 不停服升级的第一步。
-WINCH 优雅关闭子进程 “辞退所有基层员工” —— 关闭主进程（Master）下的所有工作进程（Worker）。 升级过程中，让旧版本的Worker不再接收新请求。
-QUIT （再提一次） 优雅退出主进程 “老板退休” —— 彻底关闭主进程（Master）。 升级完成后，送走旧版本的”老老板”。

记忆口诀：老板（Master）管员工（Worker）
-WINCH 是辞退所有老员工（Worker），但老板（Master）还在
-QUIT 是老板（Master）正式退休，彻底退出

方案一：重装升级（停机升级）

这是最原始、最简单的方式，但需要停服

操作步骤：

停止Nginx服务

删除旧的安装目录（rm -rf /usr/local/nginx）

下载新版本源码包，重新编译安装

适用场景：

开发环境或测试环境

线上业务允许短暂停机的维护窗口

风险提示：

操作前务必备份配置文件（conf/ 目录）和网站资源文件（html/ 目录），否则删库跑路的就是你

方案二：平滑升级（不停服升级）

核心原理（三阶段法则）

平滑升级不停止旧服务，核心逻辑就三步：

旧的不停：保持老版本Nginx继续处理当前请求

新的起来：编译新版本，启动新的主进程（Master）

平稳交接：新老Master同时运行，新的接手新请求，旧的处理完老请求后优雅退场

前言:Nginx是什么？为什么每个后端开发都要会它？

Nginx是一个高性能的HTTP和反向代理服务器，用于负载均衡，静态内容缓存，以及动态内容生成

先问大家一个问题：你写了一个PHP/Java/Python项目，怎么让外网用户访问到？

答案很简单——需要一个 Web服务器 来接收HTTP请求，再把处理结果返回给浏览器。Nginx就是目前最流行的Web服务器之一，它轻量、高并发、配置灵活，全球超过4亿个网站跑在Nginx上

打个比方：Nginx就像商场的前台小姐姐——用户来了（HTTP请求），她先判断你要去哪个楼层（路由分发），再把你的需求转给对应的柜台（后端应用），最后把结果告诉你

今天这篇教程，我会带你从零基础开始，一步步掌握Nginx的核心用法，最后用宝塔面板部署一套完整的NiuShop电商系统，让你真正体会“学以致用”

location匹配规则（新手最容易搞混的）

location 的匹配规则有优先级，我用一张表帮你理清：

写法 含义 优先级
location = /xxx 精确匹配，完全一致才命中 最高
location ^~ /xxx 前缀匹配，一旦命中就不再看正则 第二
location ~ \.php$ 正则匹配，区分大小写 第三
location ~* \.jpg$ 正则匹配，不区分大小写 第三
location /xxx 普通前缀匹配 第四
location / 默认匹配，所有没命中的都走这里 最低

举个例子：

访问 example.com/ → 命中①
访问 example.com/images/logo.png → 命中②
访问 example.com/index.php → 命中③
访问 example.com/about.html → 命中④

虚拟主机

为什么要用虚拟主机？

先问一个问题：你只有一台服务器，但手上同时有三个项目要上线，怎么办？
方案A：买三台服务器 → 钱包不同意 ❌
方案B：一台服务器跑三个Nginx实例 → 端口打架，管理混乱 ❌
方案C：一台服务器、一个Nginx、配置三个虚拟主机 → 这才是正道 ✅

这就是虚拟主机的价值所在——让一台物理服务器同时承载多个网站，每个网站拥有独立的域名、独立的目录、独立的配置，彼此互不干扰

用户访问不同的域名，Nginx会根据请求头里的域名自动路由到对应的网站目录，用户完全感觉不到这些网站跑在同一台机器上

正向代理与反向代理（理解）

正向代理

客户端（Clients）：图左侧的电脑、手机、平板它们发起了HTTP请求

关键在于：客户端是明确知道自己使用了代理的

它们需要主动在设备上配置代理服务器的IP地址和端口，才能把请求发给代理

正向代理服务器（Forward Proxy）：图中间带盾牌的服务器

它是客户端的“对外发言人”。它代表客户端去互联网（Internet）上请求目标服务器

目标服务器（Web Servers）：图右侧的目标网站（example.com）

“目标服务器看到的是代理的IP，而不是客户端的IP。” 这意味着真实的客户端IP被隐藏了

“图中的目标服务器 example.com 仅为演示。在实际应用中，目标服务器可能是 www.google.com 等外网知名站点，这就是常见的‘科学上网’场景。”

反向代理

客户端（Clients）：笔记本、手机、平板发起的请求，并不知道后端服务器的存在

它们以为自己直接访问了 47.112.206.241

反向代理（Reverse Proxy）：这就是你的阿里云Nginx，它作为“前哨”，接收所有公网请求

后端服务器（Backend Servers）：图中是 10.0.1.10、10.0.1.11、10.0.1.12，它们是局域网内的真实应用服务器（比如后端的 Tomcat、Node.js、PHP-FPM 等）

核心闭环：Nginx 收到请求后，转发（Forward Request）给后端；后端处理完毕返回响应，Nginx 再返回响应（Return Response）给客户端

正向代理是客户端的替身，替客户端访问世界；反向代理是服务器的前哨，替服务器阻挡风雨。Nginx 最强大的地方，在于它将反向代理做到了极致的高性能与高可用。”

🔍 图1：正向代理（科学上网）

场景：浏览器请求 www.google.com，但它不直接发给 Google，而是发给了“中国香港/台湾服务器”（正向代理）。

核心：代理服务器代替客户端去访问 Google。

结论：代理替客户端办事，客户端知道自己用了代理，目的服务器不知道真正是谁在访问。

🔍 图2：请求转发（反向代理的最简形态）

场景：用户（浏览器）请求 Nginx 服务器，Nginx 发现这是一个动态请求（比如 .php），于是把它转发给了后端的 PHP-FPM。

核心：隐藏了后端应用。用户以为 Nginx 就是全部，实际背后是 PHP-FPM 在处理业务逻辑。

当用户访问 http://47.112.206.241/index.php 时，Nginx 就会像图中一样，把请求“悄悄”转给本机的 PHP-FPM，用户完全无感知。

🔍 图3：反向代理（负载均衡，企业级标配）

场景：多个用户（浏览器）同时访问，Nginx 作为“流量调度员”，把请求分发给背后的 Web01、Web02、Web03 三台服务器。

核心：分流、容错、高可用。当其中一台 Web 服务器挂了，Nginx 可以自动把流量分给另外两台，保证服务不中断。

熟悉了基本反代，就可以用Node.js在这台服务器上开两个端口，然后在 Nginx 里配置 upstream 模块，实现最基础的负载均衡

Location区块

location 是 Nginx 最核心的路由匹配指令，它决定了不同的 URL 会走进哪个处理逻辑。语法如下：

五种匹配模式

  • = 精确匹配：完全等于匹配规则才触发。优先级最高。
    • 示例：location = /50x.html 只能匹配 http://domain/50x.html
  • ^~ 前缀匹配且不做正则：以某个字符串开头，匹配成功后不再去匹配后面的正则。
    • 示例：location ^~ /img/ 匹配 http://domain/img/a.jpg
  • ~ 区分大小写的正则匹配：
    • 示例：location ~ /Example/ 匹配 /Example/，但不匹配 /example/。
  • ~* 不区分大小写的正则匹配：
    • 示例：location ~* \.(jpg|jpeg|png|gif)$ 匹配所有图片后缀。
  • / 通用匹配：以上都没匹配上时，作为兜底。

优先级顺序（面试必问）

当多个 location 同时匹配时，Nginx 按以下顺序处理：

  1. 精确匹配 =（一旦命中，停止后续匹配）
  2. 前缀匹配 ^~（一旦命中，停止后续匹配）
  3. 正则匹配 ~ 或 ~*（按配置文件中出现的先后顺序）
  4. 普通前缀匹配 /

⚠️ 避坑提示：正则匹配一旦命中，就会停止匹配后续规则，因此建议把最严格的正则放在前面。

Rewrite重写与重定向：优雅的“伪装术”

rewrite 和 return 是 Nginx 实现伪静态、域名迁移和防盗链的利器。

返回状态码（return）

常用状态码：

  • 200：正常响应。
  • 301：永久重定向（域名变更首选，会被浏览器/搜索引擎缓存）。
  • 302：临时重定向。
  • 304：缓存有效，读取本地。
  • 401：未授权（账号密码错误）。
  • 403：禁止访问（权限不足）。
  • 404：资源未找到。
  • 500：服务器内部错误（代码异常）。
  • 502：网关错误（后端服务挂了，如 PHP-FPM 没启动）。
  • 504：网关超时（后端处理太慢）。

Rewrite 语法与 Flag 详解

  • last：本条规则匹配完成后，继续向下匹配新的 location 规则（常用于重写后交给 PHP 处理）。客户端 URL 地址不变。
  • break：本条规则匹配完成后，终止后续任何匹配。客户端 URL 地址不变。
  • redirect：返回 302 临时重定向，客户端 URL 地址会改变。
  • permanent：返回 301 永久重定向，客户端 URL 地址会改变。

💥 高能预警：为什么防盗链 rewrite 必须用 break 而不是 last？
如果你写 rewrite ^/ /default.png last;，Nginx 会重写为 default.png，但 default.png 同样符合正则 \.(gif|jpg|jpeg|png|bmp)$，触发死循环，导致 500 错误。使用 break 可以立即终止匹配并返回文件。

在经历了手工编译 Nginx、配置分离、安全加固等一系列硬核操作后，我们终于迎来了真正的实战——NiuShop 开源电商系统的部署。

为了模拟真实的开发交付流程，我们这次重开一台全新的阿里云服务器。这次我们不再手工敲打每一行命令，而是借助宝塔面板，体验一把企业级的高效部署流程。

一、 准备工作

重置服务器

  • 重新开启一台新服务器
  • 登录服务器终端，确认当前环境干净，没有安装过 Nginx 或 MySQL。

阿里云安全组放行

在阿里云控制台的安全组中，放行以下端口（入方向）：

  • 80/tcp（网站 HTTP 服务）
  • 443/tcp（网站 HTTPS 服务，备用）
  • 21266/tcp（宝塔面板默认端口，需要根据后续安装输出的实际端口为准）

安装宝塔面板

宝塔面板是提升运维效率的服务器管理软件，支持一键部署 LAMP/LNMP 环境。

具体安全组放行xxxxx端口，请参考面板的访问信息

一键部署 LNMP 环境

  1. 在浏览器输入宝塔面板地址（Mac 用户可能会提示证书不安全，点击“高级” -> “继续访问”即可）。
  2. 登录面板后，会弹出环境安装向导。选择 LNMP（推荐）：
    • Nginx：选择 1.26（或最新稳定版）
    • MySQL：选择 5.7（兼容性好，NiuShop 要求 5.6~8.0）
    • PHP：必须选择 7.4（NiuShop 严格要求的版本）
    • phpMyAdmin：按需安装（用于数据库可视化管理）
  3. 勾选“极速安装”，点击“一键安装”。等待约 5-10 分钟，环境即可自动配置完成。

⚠️ 避坑提示：安装 PHP 时，务必确认勾选了 fileinfo 扩展。如果没有，后续可以进入“软件商店” -> PHP 7.4 -> 设置 -> 安装扩展，手动安装 fileinfo。

💡 环境装好后，千万别忘了补装“三件套”：

安装 Redis：“软件商店”搜索 Redis 并安装（NiuShop 强依赖，否则装不上）。

安装 fileinfo和redis 扩展：软件商店 -> PHP 7.4 -> 设置 -> 安装扩展，找到 fileinfo和redis 并安装（NiuShop 环境检测必须项）。

调整 PHP 内存：在 PHP 7.4 的配置修改里，将 memory_limit 改为 512M（避免安装或运行报错）

创建站点与上传源码

创建站点

  • 在宝塔面板左侧菜单点击网站 -> 添加站点。
  • 域名填写你的公网 IP（如 47.112.206.241）或已备案域名。
  • 创建 MySQL 数据库（记录下数据库名、用户名、密码）。
  • PHP 版本选择 7.4。

上传源码

  • 进入刚创建的站点根目录（/www/wwwroot/你的域名或IP）。
  • 上传 niushop.zip 源码包。
  • 在宝塔面板中双击压缩包，解压到当前目录。
  • 调整项目目录：NiuShop 的入口在 public 目录下。所以在宝塔面板中点击“网站”->“设置”->“网站目录”，将“运行目录”改为 /public，并保存。

  2. 浏览器访问：在 Mac 浏览器输入 http://www.shop.com。
  3. 填写安装信息：
    • 数据库主机：localhost
    • MySQL 端口：3306
    • 数据库用户：你创建站点时生成的用户名

    • 数据库名称：你创建站点时生成的数据库名
    • 数据表前缀：ns
    • Redis 主机：127.0.0.1，端口 6379，密码留空

  1. 在宝塔面板的“网站”中，点击你的站点对应的“设置”。

日常运维与排错

  • 查看日志：在宝塔面板可以直接查看网站日志、MySQL 错误日志和 PHP-FPM 日志。
    • 网站日志：/www/wwwlogs/你的域名.log
    • MySQL 错误日志：/www/server/data/mysql.err
    • PHP 错误日志：/www/server/php/74/var/log/php-fpm.log
  • 遇到 502 Bad Gateway：通常是 PHP-FPM 没启动或崩溃，去“软件商店”重启 PHP 7.4。
  • 遇到 403 Forbidden：检查站点目录权限，确保所有者为 www。在宝塔中可以使用“文件”管理器的“权限”功能进行修正。
  • 遇到 404 Not Found：99% 是伪静态没有配置，或者运行目录没有指向 public。

📝 总结

通过全新的宝塔面板部署，我们省去了手工编译 Nginx、安装 PHP 扩展的繁琐过程，将主要精力集中在项目本身的配置（如运行目录、伪静态、数据库连接）上。这也是企业开发中常用的提效方案。
