Kubernetes 资源管理与 Pod 进阶：从调度到生命周期全解析

在 Kubernetes 集群中，Pod 是最小的部署单元，但如何让 Pod 恰到好处地运行在合适的节点上？Pod 启动后如何保证它的健康状态？这些问题是每一个 K8s 使用者都必须掌握的核心技能。今天，我们就从 Pod 的创建流程讲起，逐步深入调度策略、生命周期管理以及健康检查，最后附上常见故障排查技巧。无论你是刚入门的新手，还是有一定经验的开发者，这篇文章都能帮你构建完整的知识体系。

Pod 是如何被创建出来的？

很多人以为执行 kubectl create pod 后，Pod 就“嗖”地一下出现了。实际上，这背后有一套精密的协作流程。

Step 1：用户提交 Pod 定义
我们通过 kubectl 向 API Server 发起创建 Pod 的请求，这通常是一个 YAML 或 JSON 文件。

Step 2：API Server 接收并持久化
API Server 收到请求后，并不会直接创建 Pod，而是生成一份标准的 YAML 描述，并将其写入 etcd 数据库。此时，仅仅是在 etcd 中多了一条记录，没有任何容器被启动。

Step 3：调度器（Scheduler）介入
Scheduler 通过 watch 机制检测到新的 Pod 对象（且 pod.spec.nodeName 为空），于是执行调度算法，在所有可用节点中选出最适合的一个，然后把节点名称写回到 Pod 的 spec.nodeName 字段，并更新 etcd。

Step 4：节点上的 kubelet 真正创建容器
每个节点上的 kubelet 也在持续监听 etcd 中的变化。当它发现某个 Pod 的 nodeName 指向自己时，就会调用本地的容器运行时（如 Containerd）来创建实际的容器。

整个流程就像是一个接力赛：用户提交 → API Server 记录 → Scheduler 选址 → Kubelet 执行。理解这个过程，对我们后续排查“Pod 一直 Pending”的问题非常有帮助。

Pod 调度策略：让 Pod 去它该去的地方

默认情况下，Scheduler 会根据资源均衡等算法自动选择节点。但实际生产中，我们经常需要干预调度，比如把需要 GPU 的 Pod 放到有 GPU 的节点上，或者把两个频繁通信的 Pod 放在一起以减少网络延迟。Kubernetes 提供了四大类调度方式。

亲和性调度（更灵活的选择）

亲和性调度分为硬亲和（required）和软亲和（preferred）。硬亲和是必须满足的条件，否则 Pod 不会调度；软亲和则是优先满足，如果没有合适的节点，也会调度到其他节点。

污点（Taints）与容忍（Toleration）

前面都是从 Pod 角度“主动选择”节点。污点则是从节点角度“拒绝”Pod。节点上可以设置污点，Pod 可以通过容忍来“忽略”这些拒绝。

污点的格式是 key=value:effect，effect 有三种：

  • PreferNoSchedule：尽量不调度，但非强制。
  • NoSchedule：一定不调度新 Pod，但不影响已有 Pod。
  • NoExecute：不仅不调度新 Pod，还会驱逐已有的不匹配的 Pod。

Pod 的生命周期与健康检查

Pod 从创建到终止，经历了一系列状态变化，我们可以利用这些阶段来做很多自动化的事情。

生命周期概览

  1. Pending：Pod 已被创建，但尚未调度完成或镜像拉取中。
  2. Running：所有容器已创建，至少有一个容器正在运行。
  3. Succeeded 或 Failed：所有容器正常终止（退出码 0）或异常终止（非 0）。
  4. Unknown：无法获取 Pod 状态，通常因为 kubelet 与 API Server 通信中断。

在容器运行过程中，Kubernetes 提供了三种探针（Probe）来检测容器的健康状况：

  • livenessProbe（存活探针）：检测容器是否“活着”。如果失败，kubelet 会重启该容器。
  • readinessProbe（就绪探针）：检测容器是否“准备好”接收流量。如果失败，Pod 会从 Service 的 Endpoints 中移除，不接收请求。
  • startupProbe（启动探针）：用于慢启动容器，在启动成功之前，不会让 liveness 和 readiness 干扰。

三种探测方式

  1. Exec：在容器内执行命令，返回码为 0 表示成功。
  2. HTTPGet：访问容器的 HTTP 端点，状态码 200~399 表示成功。
  3. TCPSocket：尝试与容器的指定端口建立 TCP 连接，成功则表示健康。
案例：liveness-exec

创建一个 Pod，容器启动后创建文件 /tmp/healthy，30 秒后删除。存活探针每隔 5 秒检查该文件是否存在，若不存在则重启容器。

案例：readiness 与 liveness 组合

一个 Pod 可以同时配置就绪探针和存活探针。通常，就绪探针用于控制流量接入，存活探针用于保证容器运行。两者探测路径、端口可以相同，但作用不同。

常见故障排查与状态解读

Pod 状态 含义与排查思路
Pending 调度未完成或镜像拉取慢。检查 kubectl describe pod 查看事件，看是否因资源不足、节点污点、节点选择器不匹配等。
CrashLoopBackOff 容器反复启动又崩溃。使用 kubectl logs <pod> 查看容器日志，检查启动命令、依赖环境是否正确。
Running 但 0/1 Ready 就绪探针失败，流量不会转发。检查 readinessProbe 配置的路径、端口是否正确。
Failed 容器退出码非 0。查看日志和退出码，通常是程序内部错误。
Unknown API Server 与 kubelet 通信中断，检查节点网络或 kubelet 状态。

总结与最佳实践

  • 调度策略：根据实际场景选择合适的调度方式。硬亲和（required）适合强制隔离，软亲和（preferred）适合弹性均衡。污点和容忍常用于专用节点（如 GPU 节点）或保护系统组件。
  • 健康检查：必配！至少配置 livenessProbe 和 readinessProbe。liveness 保证容器不死，readiness 保证流量不误发。探测方式优先选择 HTTPGet 或 TCP，因为它们更贴近应用实际。
  • 生命周期钩子：善用 postStart 做初始化，用 preStop 做优雅关闭，但注意 postStart 不能太耗时，否则会阻塞容器启动。
  • 故障排查：永远从 kubectl describe 和 kubectl logs 开始，它们提供了 80% 的线索。
